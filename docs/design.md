# duckscout 設計

## 目的と範囲

平坦な空間で指定された対象をカメラで探し、歩いて近づいて停止する。対象は色のついた既知サイズの単純な物体を基本とする。歩行には公式の学習済み方策を利用し、認識から行動判断までの接続を独自実装する。

音声操作、物体の把持、歩行方策の新規学習は対象範囲に含めない。

## 実行基盤

Python 3.12とuvを使用する。公式RLプロジェクトがPython `>=3.12,<3.13` を指定しているため、Pythonのバージョンを合わせる。表示・推論に必要な依存に絞り、プロジェクト専用の `.venv/` に隔離する。

物理シミュレーションはMuJoCo、歩行は公式ONNX方策のCPU推論を採用する設計とする。アプリの起動入口は `python -m duckscout` に統一し、互換用の起動スクリプトは設けない。macOSのGUI実行時に内部で `mjpython` へ切り替える。切り替え済みの判定にはアプリ専用の環境変数を一度だけ読み取って削除し、MuJoCoの非公開APIに依存しない。headless実行では切り替えない。uv管理のPythonでは仮想環境のシンボリックリンクから共有ライブラリを解決できない場合があるため、実行中のPythonが提供するライブラリディレクトリを起動プロセスの探索パスに追加する。設定形式はTOMLとする。

参照：[公式環境定義](https://github.com/pollen-robotics/microduck_rl/blob/develop/pyproject.toml)、[公式推論手順](https://github.com/pollen-robotics/microduck_rl#readme)、[MuJoCo passive viewer](https://mujoco.readthedocs.io/en/stable/python.html#passive-viewer)。実行に使用する上流revisionは固定する。

## 責務とデータの流れ

```text
カメラ画像 → 対象検出 → 行動判断 → 移動指令 → 歩行方策
     ↑                                       ↓
     └──────── シミュレーション ← 関節制御 ────┘
```

| モジュール | 責務 |
|---|---|
| `__main__.py` | 引数解析、起動環境の準備 |
| `simulation.py` | MuJoCo状態、BAM関節制御、初期化、物理更新、表示 |
| `locomotion.py` | 方策・関節の互換性検証、観測生成、ONNX推論、関節目標角への変換 |
| `perception.py` | カメラ画像から対象の位置・見え方を推定 |
| `behavior.py` | 探索・接近・停止の判断、移動指令の生成 |
| `evaluation.py` | 成否・所要時間・停止距離などの記録 |

物理状態の更新はシミュレーション側に集約する。行動判断側は関節を直接操作しない。

`Simulation` は `dataclass(kw_only=True, eq=False)` とし、クラス先頭に依存関係と内部状態を型付きで宣言する。MuJoCoのmodel・data、初期keyframeのID、BAMモデル、方策を構築時に受け取り、モーター制御器・ステップ数・立位の計測値は `field(init=False)` で内部管理する。通常の生成には `Simulation.from_scene()` を使い、同じMuJoCoモデルに対応する依存関係の組み立てを集約する。生成時にリセットまで行い、使用可能な初期状態を返す。

`LocomotionPolicy` もdataclassでMuJoCoモデルと推論セッションを受け取る。関節・センサーのアドレス、入出力名、前回のactionは `init=False` とし、構築時に互換性を検証する。通常は `from_onnx()` でCPUセッションを読み込み、テストではセッションを直接渡す。BAMのモーター・摩擦設定は同じシミュレーションモジュールの `configure_bam()` にまとめる。

方策とロボットの互換性には、観測順序、関節順序、正規化、制御周期、アクチュエータモデル、XMLの整合が必要となる。ONNXの読込成功だけでは歩行再現の成立を判断できない。

物理更新・方策推論・画像認識はそれぞれ必要な周期で処理し、画像認識が姿勢制御を妨げない構成とする。周期と並列化方式は実測に基づいて決める。

## 移動制御

公式の `velstand.onnx` をONNX RuntimeのCPUプロバイダで実行する。推論は50 Hz、物理更新とBAM制御は200 Hz。物理ステップ数を基準に4ステップごとに推論し、間は目標角を保持する。一時停止中は物理・推論ともに進めない。

観測はfloat32の61要素で、順序は次のとおり。

| 要素 | 次元 | 内容 |
|---|---|---|
| 角速度 | 3 | `imu_ang_vel` センサーの値 |
| 重力方向 | 3 | 単位重力ベクトルを胴体座標系へ変換 |
| 関節角 | 14 | 公式の基準姿勢からの差 |
| 関節速度 | 14 | 対応する関節の速度 |
| 前回の出力 | 14 | 前回推論した生のaction |
| 指令 | 13 | 移動3・頭部4・胴体6。立位ではすべてゼロ |

関節順序は左脚5、首・頭4、右脚5。名前とアクチュエータの接続先からモデルの互換性を確認する。ONNX内に観測の正規化が含まれるため、入力側では追加の正規化をしない。14要素の出力を基準姿勢へ加算し（action scale = 1.0）、BAMへ目標角として渡す。非有限値・不正な入出力形状は実行を停止する。

BAMは公式CPU推論実装に合わせ、XL330のM6モデル、ファームウェアkp = 200、電圧7.4 V、電圧降下係数0.1、下限電圧6.0 V、電流制限なしを使う。XMLの位置アクチュエータをメモリ上でトルクモーターへ変換し、摩擦・減衰・慣性をBAMが扱う。ダウンロードしたXMLは書き換えない。

初期状態は胴体位置(0, 0, 0.125 m)、直立の向き、公式推論実装の基準関節角とする。リセットでは物理状態、推論履歴、制御周期、BAMの内部状態・摩擦・減衰を初期化する。

実行中は平坦な床を前提に、胴体高さが0.08 m以上、鉛直からの傾きが45度以下であることを毎ステップ確認する。水平移動は許容し、初期位置からの変位を終了条件には使わない。これらは本プロジェクトの転倒検出の閾値であり、上流の評価基準ではない。区間内の最低高さ・最大傾き・最大水平変位をheadless実行の終了時に報告する。微小な足踏み、接触状態、姿勢の見た目はこの条件だけでは評価できない。

移動指令の入口は `Simulation.set_command(forward=..., yaw_rate=...)` とし、方策の13要素の指令の先頭と3番目へ設定する。前進はロボット座標系のm/s、旋回はrad/sで左回りを正とする。前進は0〜0.30 m/s、旋回は±0.80 rad/sの有限値に限定し、範囲外は変更前に拒否する。横移動・頭・胴体の指令はゼロに固定する。キー操作は前進・その場旋回・停止のいずれかへ指令を置き換え、押下中の継続入力には依存しない。

停止は両指令をゼロにする操作であり、方策のaction履歴・物理速度を消さず、50 Hzの姿勢制御と200 Hzの物理更新を続ける。Spaceは指令を保持して時間を止め、Rは指令・履歴・物理状態を初期化する。GUIコールバックはキーをキューへ入れるだけとし、指令変更も物理更新と同じスレッドで適用する。

動作テストでは2秒立位・5秒移動・5秒停止を前進／左右旋回それぞれに実施する。前進は15 cm超かつ横ずれ10 cm未満、旋回は指定方向へ1 rad超かつ水平変位10 cm未満を確認する。停止は3秒の整定猶予後、最後の2秒で平均水平速度0.02 m/s未満、平均絶対旋回速度0.10 rad/s未満、区間内の水平ずれ0.02 m未満・向きの変動幅0.10 rad未満を確認する。旋回後の前進は開始時のロボットの向きを基準に評価する。立位だけの30秒試験では水平ずれ10 cm未満も確認する。

方策の学習タスクは `Mjlab-VelStand-Rough-Backlash-MicroDuck`。ここでは公式CPU推論の平坦な床・`robot_groundcontact.xml` を使う。学習側の全身衝突モデル、ギアの遊び、荒地、ランダム外乱・個体差・遅延は再現していないため、学習環境の完全な再現や実機性能の保証にはならない。

参照：[公式CPU推論](https://github.com/pollen-robotics/microduck_rl/blob/b02fdea4902c2b93b7d34a83a6f05da4ececb7d3/scripts/infer_policy.py)、[方策manifest](https://huggingface.co/pollen-robotics/microduck-policies/blob/665ae4eb20bfe13bca1ef4ea6d4bb6b4a096e448/manifest.json)。

## シーンとロボット視点

独自シーン `assets/scenes/search.xml` は固定版の公式シーンをincludeし、赤い対象物を追加する。meshdirは独自シーンから公式メッシュへの相対パスを明示する。対象は一辺0.08 mの立方体で、中心位置は(0.8, 0, 0.04 m)。worldbody直下の固定geomとし、関節を追加せず、ロボットの自由度・方策の関節順序を維持する。対象との衝突は有効とする。

頭部の `jaw_soft` bodyに属する既存の `head_camera` を使用する。固定版の上流カメラ姿勢 `quat="0 0 -1 0"` はMuJoCoのカメラ軸（−Zが前、+Yが上）では後方・横向きになるため、この姿勢の場合に限り読み込み時のMjSpecで `quat=(√0.5, 0, 0, −√0.5)` に補正する。位置と画角は上流定義を維持し、垂直画角は45度。公式ファイルは書き換えず、頭部関節の動きにはそのまま追従する。実機のカメラ校正を再現するものではない。

画像取得には公開APIの `mujoco.Renderer` を使用する。GUI実行中は単一のrendererを保持し、320×240のuint8 RGB画像をシミュレーション時間基準で10 Hzで取得する。物理・方策と同じスレッドで同期処理し、終了時にはコンテキストマネージャーで解放する。画像取得前に `mj_kinematics` と `mj_camlight` で最新姿勢を反映し、物理積分や制約ソルバーの再実行は行わない。物理更新は実時間の予定時刻を基準にし、描画待ちの後は固定時間刻みのまま最大20ステップをまとめて進める。長時間停止後の追いつきはそこで打ち切り、キー操作への応答を維持する。処理能力を超える継続的な負荷では実時間より遅くなる。

外部追従視点と頭部視点の切り替えは標準ビューアのカメラ選択を利用する。保存画像は常に頭部視点から取得し、ビューアの視点・選択マークには依存しない。PPM保存は明示的なキー操作またはheadlessの保存オプションで行い、標準ライブラリで書き込む。headlessの手動モードでは保存指定時のみ描画コンテキストを作成し、最終状態を1枚取得する。自動モードでは行動判断に必要な画像を継続的に取得する。

参照：[MuJoCo Python API](https://mujoco.readthedocs.io/en/3.10.0/python.html)、[カメラ座標系](https://mujoco.readthedocs.io/en/3.10.0/XMLreference.html#body-camera)。

## 対象検出

`perception.py` の `detect_target(rgb)` はuint8のRGB画像だけを受け取り、検出結果または `None` を返す。MuJoCoの状態・対象物の正解位置・物体IDを入力に使わない。`Detection` は変更不可のdataclassで、検出枠 `(x, y, width, height)`、赤い画素の重心 `(cx, cy)`、赤い画素数 `area` を持つ。画像左上を原点とし、xは右、yは下へ増加する。検出枠の右端・下端は範囲に含めない。面積は信頼度ではない。

OpenCVのRGB→HSV変換を使用し、色相0〜10または170〜179、彩度120以上、明度50以上を赤とする。8近傍でつながった領域を抽出し、赤い画素数が最大の領域を選ぶ。25画素未満なら未検出とする。画像全体の赤い点を一つの枠にまとめず、領域ごとに扱うことで孤立したノイズを除外する。画面端の部分的な対象も面積条件を満たせば検出する。検出器は同色の別物体を識別せず、確信度は推定しない。

`annotate_detection()` は元画像をコピーし、枠・重心・検出状態を重ねる。画像取得ごとに検出し、未検出時には以前の枠を保持しない。表示用画像を次の認識入力へ戻さない。

画像処理にはGUIなしの `opencv-python-headless` を使用する。`simulation.py` は元画像の取得、検出処理の呼び出し、保存、ビューアへの表示を担当する。表示には導入済みMuJoCoの公開API `Handle.viewport`・`set_images()`・`clear_images()` を使用し、描画領域の右下に4:3の小窓を配置する。画像は最大2倍、描画領域の幅のおよそ1/3に収まるよう拡縮する。縦反転は `set_images()` に任せ、ビューアのロック外から呼ぶ。画像の転送は新しいカメラ画像が得られた場合と描画領域が変わった場合だけ行い、ビューアの同期ごとに同じ画像を再転送しない。新たなGUIウィンドウやスレッドは作らない。

保存時は同一フレームの元画像と検出結果付き画像を別ファイルに出力する。元画像のパスに対して後者のstemへ `_detection` を付け、両方をPPM形式で保存する。

## 行動判断

`behavior.py` の `Behavior` はdataclassとし、画像幅・距離しきい値・時間条件を構築時に設定する。現在の状態・検出継続時刻・見失い開始時刻などは `init=False` で内部管理する。入力は検出結果・推定距離・シミュレーション時刻だけとし、移動指令 `(forward, yaw_rate)` を返す。MuJoCoや対象の正解座標には依存しない。`simulation.py` が10 Hzの画像取得時に呼び、`Simulation.set_command()` へ適用する。

距離推定は `perception.estimate_distance()` が担当する。画像の高さH、垂直画角θから焦点距離を画素単位で `f = H / (2 tan(θ/2))` とし、対象の既知高さ0.08 mと検出枠の高さhから `d ≈ f × 0.08 / h` を求める。これは光軸方向の距離の概算で、カメラから対象までの3次元距離とは一致しない。立方体の上面・側面、カメラの傾きにより見かけの高さが変わる。検出枠が画像端から1画素以内に接する場合は、欠けによる誤推定を避けるため距離不明とする。

| 状態 | 指令と遷移 |
|---|---|
| SEARCH | 開始後1秒は立位、その後は旋回指令±0.80 rad/sで探索。検出時は停止して0.2秒の継続を確認 |
| ALIGN | 対象中心が画像中央から幅の6%以内に入るまでその場旋回 |
| APPROACH | 前進指令0.30 m/s。横ずれが幅の12%を超えたらALIGNへ戻る |
| ARRIVED | 推定距離0.40 m以下で停止し、近距離判定が0.2秒続いたら到着を保持 |
| TIMED_OUT | 開始から60秒で到着できなければ停止を保持 |
| MANUAL | 自動指令の適用を止め、手動指令を保持 |

近距離の確認中は0.43 mまでの揺れを許容し、それより離れた推定値になれば到着確認をやり直す。中央合わせと接近で許容幅を変えることで状態の頻繁な切り替えを抑える。距離不明のときは前進しない。対象喪失時は最初の未検出で移動指令をゼロにし、0.5秒の間に復帰しなければ最後に向きを合わせた旋回方向で探索へ戻る。再検出時も継続確認を行う。到着・時間切れ後は検出が変わっても自動で再発進しない。

停止は移動指令をゼロにし、方策履歴と物理速度を保持して姿勢制御を続ける。Spaceはシミュレーション時刻を止めるため、待ち時間・制限時間も進まない。矢印キーは自動動作を解除して手動へ切り替える。Rはロボットと判断状態を初期化し、起動時に `--auto` が指定されていれば自動動作を再び有効にする。状態、動作理由、現在の推定距離を小窓に表示する。転倒・非有限値は既存の物理検証で実行を終了する。

`--target X Y` は読み込み時のMjSpecで対象の配置だけを変更する。対象の正解座標は行動判断に渡さず、評価にのみ使用する。自動モードは立位・移動方策と頭部カメラを必要とし、headlessでも継続的にRGB画像を取得する。

## 再現性と評価

外部素材は固定revisionで取得し、通常起動で自動更新しない。取得時はモデル素材をGit blobハッシュ、ONNX方策をSHA-256とサイズで検証し、取得結果のSHA-256をローカルに記録する。素材と方策の対応を記録する。出典・ライセンス・改変内容の管理は `THIRD_PARTY_NOTICES.md` に従う。

試行ごとに配置、乱数seed、設定、方策revision、コードrevisionを保存する。成功条件は対象の発見と接近後の停止とし、距離・時間・姿勢安定性の閾値を明示する。複数配置について成功率・所要時間・停止距離・失敗理由を比較する。

公式の学習済み方策の利用部分と独自の認識・行動判断を区別し、成功例と失敗例を説明する。提出物は1〜3分の動画、公開コード、PDFレポートとする。提出条件の根拠は10月19日版の課題資料。
