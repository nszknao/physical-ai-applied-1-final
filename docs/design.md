# duckscout 設計

## 目的と範囲

平坦な空間で指定された対象をカメラで探し、歩いて近づいて停止する。対象は色のついた既知サイズの単純な物体を基本とする。歩行には公式の学習済み方策を利用し、認識から行動判断までの接続を独自実装する。

音声操作、物体の把持、歩行方策の新規学習は対象範囲に含めない。

## 実行基盤

Python 3.12とuvを使用する。公式RLプロジェクトがPython `>=3.12,<3.13` を指定しているため、Pythonのバージョンを合わせる。表示・推論に必要な依存に絞り、プロジェクト専用の `.venv/` に隔離する。

物理シミュレーションはMuJoCo、歩行は公式ONNX方策のCPU推論を採用する設計とする。アプリの起動入口は `python -m duckscout` に統一し、互換用の起動スクリプトは設けない。macOSのGUI実行時に内部で `mjpython` へ切り替える。切り替え済みの判定にはアプリ専用の環境変数を一度だけ読み取って削除し、MuJoCoの非公開APIに依存しない。headless実行では切り替えない。uv管理のPythonでは仮想環境のシンボリックリンクから共有ライブラリを解決できない場合があるため、実行中のPythonが提供するライブラリディレクトリを起動プロセスの探索パスに追加する。設定形式はTOMLとする。

参照：[公式環境定義](https://github.com/pollen-robotics/microduck_rl/blob/develop/pyproject.toml)、[公式推論手順](https://github.com/pollen-robotics/microduck_rl#readme)、[MuJoCo passive viewer](https://mujoco.readthedocs.io/en/stable/python.html#passive-viewer)。実行に使用する上流revisionは固定する。

## 責務とデータの流れ

```text
カメラ画像 → 対象検出 → 行動判断 → 移動指令 → 歩行方策
     ↑                                       ↓
     └──────── シミュレーション ← 関節制御 ────┘
```

| モジュール | 責務 |
|---|---|
| `__main__.py` | 引数解析、起動環境の準備 |
| `simulation.py` | MuJoCo状態、BAM関節制御、初期化、物理更新、表示 |
| `locomotion.py` | 方策・関節の互換性検証、観測生成、ONNX推論、関節目標角への変換 |
| `perception.py` | カメラ画像から対象の位置・見え方を推定 |
| `behavior.py` | 探索・接近・停止の判断、移動指令の生成 |
| `evaluation.py` | 成否・所要時間・停止距離などの記録 |

物理状態の更新はシミュレーション側に集約する。行動判断側は関節を直接操作しない。

`Simulation` は `dataclass(kw_only=True, eq=False)` とし、クラス先頭に依存関係と内部状態を型付きで宣言する。MuJoCoのmodel・data、初期keyframeのID、BAMモデル、方策を構築時に受け取り、モーター制御器・ステップ数・立位の計測値は `field(init=False)` で内部管理する。通常の生成には `Simulation.from_scene()` を使い、同じMuJoCoモデルに対応する依存関係の組み立てを集約する。生成時にリセットまで行い、使用可能な初期状態を返す。

`StandingPolicy` もdataclassでMuJoCoモデルと推論セッションを受け取る。関節・センサーのアドレス、入出力名、前回のactionは `init=False` とし、構築時に互換性を検証する。通常は `from_onnx()` でCPUセッションを読み込み、テストではセッションを直接渡す。BAMのモーター・摩擦設定は同じシミュレーションモジュールの `configure_bam()` にまとめる。

方策とロボットの互換性には、観測順序、関節順序、正規化、制御周期、アクチュエータモデル、XMLの整合が必要となる。ONNXの読込成功だけでは歩行再現の成立を判断できない。

物理更新・方策推論・画像認識はそれぞれ必要な周期で処理し、画像認識が姿勢制御を妨げない構成とする。周期と並列化方式は実測に基づいて決める。

## 立位制御

公式の `velstand.onnx` をONNX RuntimeのCPUプロバイダで実行する。推論は50 Hz、物理更新とBAM制御は200 Hz。物理ステップ数を基準に4ステップごとに推論し、間は目標角を保持する。一時停止中は物理・推論ともに進めない。

観測はfloat32の61要素で、順序は次のとおり。

| 要素 | 次元 | 内容 |
|---|---|---|
| 角速度 | 3 | `imu_ang_vel` センサーの値 |
| 重力方向 | 3 | 単位重力ベクトルを胴体座標系へ変換 |
| 関節角 | 14 | 公式の基準姿勢からの差 |
| 関節速度 | 14 | 対応する関節の速度 |
| 前回の出力 | 14 | 前回推論した生のaction |
| 指令 | 13 | 移動3・頭部4・胴体6。立位ではすべてゼロ |

関節順序は左脚5、首・頭4、右脚5。名前とアクチュエータの接続先からモデルの互換性を確認する。ONNX内に観測の正規化が含まれるため、入力側では追加の正規化をしない。14要素の出力を基準姿勢へ加算し（action scale = 1.0）、BAMへ目標角として渡す。非有限値・不正な入出力形状は実行を停止する。

BAMは公式CPU推論実装に合わせ、XL330のM6モデル、ファームウェアkp = 200、電圧7.4 V、電圧降下係数0.1、下限電圧6.0 V、電流制限なしを使う。XMLの位置アクチュエータをメモリ上でトルクモーターへ変換し、摩擦・減衰・慣性をBAMが扱う。ダウンロードしたXMLは書き換えない。

初期状態は胴体位置(0, 0, 0.125 m)、直立の向き、公式推論実装の基準関節角とする。リセットでは物理状態、推論履歴、制御周期、BAMの内部状態・摩擦・減衰を初期化する。

立位確認は平坦な床を前提に、胴体高さが0.08 m以上、鉛直からの傾きが45度以下、初期位置からの水平ずれが0.10 m以下であることを毎ステップ確認する。これらは本プロジェクトの転倒・大きな移動を検出する閾値であり、上流の評価基準ではない。区間内の最低高さ・最大傾き・最大水平ずれをheadless実行の終了時に報告する。微小な足踏み、接触状態、姿勢の見た目はこの条件だけでは評価できない。

方策の学習タスクは `Mjlab-VelStand-Rough-Backlash-MicroDuck`。ここでは公式CPU推論の平坦な床・`robot_groundcontact.xml` を使う。学習側の全身衝突モデル、ギアの遊び、荒地、ランダム外乱・個体差・遅延は再現していないため、学習環境の完全な再現や実機性能の保証にはならない。

参照：[公式CPU推論](https://github.com/pollen-robotics/microduck_rl/blob/b02fdea4902c2b93b7d34a83a6f05da4ececb7d3/scripts/infer_policy.py)、[方策manifest](https://huggingface.co/pollen-robotics/microduck-policies/blob/665ae4eb20bfe13bca1ef4ea6d4bb6b4a096e448/manifest.json)。

## 行動判断

- 対象の正解座標を行動判断に渡さず、評価にのみ使用する。
- 距離推定の基本案は、既知サイズの対象と画像上の大きさを使う方法とする。
- 到着時は移動指令をゼロにし、姿勢制御を続ける。
- 対象喪失時は前進を止めて再探索する。
- 転倒・非有限値・時間切れなど継続不能な場合は試行を終了し、理由を記録する。
- 停止距離、許容誤差、対象喪失の猶予時間、再検出条件は設定値として扱う。

## 再現性と評価

外部素材は固定revisionで取得し、通常起動で自動更新しない。取得時はモデル素材をGit blobハッシュ、ONNX方策をSHA-256とサイズで検証し、取得結果のSHA-256をローカルに記録する。素材と方策の対応を記録する。出典・ライセンス・改変内容の管理は `THIRD_PARTY_NOTICES.md` に従う。

試行ごとに配置、乱数seed、設定、方策revision、コードrevisionを保存する。成功条件は対象の発見と接近後の停止とし、距離・時間・姿勢安定性の閾値を明示する。複数配置について成功率・所要時間・停止距離・失敗理由を比較する。

公式の学習済み方策の利用部分と独自の認識・行動判断を区別し、成功例と失敗例を説明する。提出物は1〜3分の動画、公開コード、PDFレポートとする。提出条件の根拠は10月19日版の課題資料。
